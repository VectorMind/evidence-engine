# Deep Survey of Python Projects That Put an Indexing Layer on Top of Docling

## Bottom line

If the goal is **an open, Python-first, Docling-based indexing system that does not hide retrieval behind an agent framework**, the best currently documented fit is **txtai**. It is the only clearly documented Docling integration I found that combines Docling extraction with a **local SQL-backed content store** and **SQL query support**, with SQLite as the default and DuckDB as another supported local option. It also supports semantic retrieval, hybrid sparse+dense search, and SQL-native filtering. The tradeoff is that txtai uses Docling primarily as an extraction backend and then indexes text/metadata, so it is **not a Docling-native block graph** that preserves every document element as a first-class stored object. citeturn29search0turn35view0turn35view1turn35view2turn35view3turn37view0

If the goal is instead **the strongest open local retrieval stack with Docling-aware structure, multimodal search, and hybrid retrieval**, **haiku.rag** is the most impressive current project. It uses **LanceDB**, supports **hybrid vector + full-text retrieval**, stores the **full `DoclingDocument`** for structure-aware context expansion, supports **visual grounding** and multimodal search, and even includes a production ingester with a **persistent SQLite queue**. The tradeoff is that it is much more opinionated and agentic than what you asked for. citeturn20view0turn9search0turn9search1turn9search9

If the goal is **inspection, controllable ingestion, optional search indexing, and exploratory graph/query interfaces**, **Docling Studio** is the best public reference implementation. It uses **SQLite** for app storage, can optionally push chunks into **OpenSearch** for vector and full-text retrieval, and can mirror the full Docling tree into **Neo4j**, making sections, paragraphs, tables, figures, pages, and chunks queryable as graph nodes. That makes it an excellent proof that a Docling-native structural store is useful, but it is a studio/product rather than a small embedded library. citeturn23view0

The larger conclusion is that your instinct is right: **Docling is already rich enough to be the front half of a serious local indexer, but the ecosystem still mostly flattens it into chunks**. Public projects keep reinventing the mapping because vector stores like Chroma, Milvus, and even many framework integrations are optimized around chunks and embeddings, while Docling’s real value is its **hierarchy, tables, pictures, page provenance, and multimodal structure**. The gap is not “can this be built?” but “what is the canonical flattening of a `DoclingDocument` into durable, queryable storage without losing the good parts?” citeturn14search9turn30view0turn30view1turn31search2turn20view0turn23view0

## What Docling already solves for an indexer

Docling already gives an indexer much more than ordinary OCR-and-split pipelines. It supports a broad set of relevant formats including **PDF, DOCX, PPTX, XLSX, HTML, images, and more**; for PDFs it adds **layout analysis, reading order, table structure, code, formulas, image classification, and OCR**; and it normalizes results into a unified **`DoclingDocument`** representation with text, tables, pictures, hierarchy, layout information, and provenance. It can export to **Markdown, HTML, DocTags, and lossless JSON**. citeturn14search6turn14search9turn26search3turn29academia10

That unified document model matters because it is precisely what most downstream indexers throw away. Docling’s own documentation describes `DoclingDocument` as a pydantic model that can represent **text, tables, pictures, document hierarchy, main-body versus furniture, layout metadata, and provenance**. In other words, the “indexing substrate” already exists; the missing piece is a canonical durable search schema on top of it. citeturn14search9

For the specific multimodal features you care about, Docling already exposes unusually strong lower-layer signals. It supports **OCR**, including multiple OCR engines; **picture classification**, where figures can be classified into document-relevant classes such as **chart types, flow diagrams, logos, signatures, and more**; **picture description/captioning** with local or remote vision models; and even **chart data extraction** exposed in the CLI for bar, pie, and line charts. It also supports **visual grounding** by preserving page images, so retrieved chunks can be tied back to page visuals. citeturn14search7turn27view1turn14search2turn14search0turn14search5

Docling also treats markup-oriented formats differently from low-level visual formats, which is important for your “special treatment of Markdown parsing” requirement. The Docling paper explains that **markup-based formats such as MS Office, HTML, and Markdown preserve semantic structure** and can be routed through direct parser backends, while low-level formats like PDFs and scanned images require more recovery through OCR, layout analysis, and table recognition. That means a good Docling-based indexer should not apply the same flattening logic to Markdown and scanned PDF. citeturn29search5turn14search6

## The current project landscape

### Closest matches to the system you want

**txtai** is the closest public, documented match to your requirements. Docling is an official integration in the Docling ecosystem, and txtai’s core abstraction is an **embeddings database** that explicitly combines vector indexes, relational storage, and keyword search. txtai supports **vector search with SQL**, and its storage format documentation shows that local content storage can use **SQLite** or **DuckDB**. Its query layer supports SQL through `embeddings.search`, including the `similar()` clause, and it can combine a similarity index with relational filtering. In the actual implementation of its file-to-HTML pipeline, txtai can choose a **Docling backend**, instantiate `DocumentConverter`, and export Docling output to HTML before indexing. This is exactly the kind of pragmatic “open extraction plus honest index” layering you are describing. citeturn29search0turn35view0turn35view1turn35view2turn35view3turn37view0turn38view0

The limit of txtai is not openness but **granularity**. It is open and SQL-capable, but it does not present a canonical, first-class relational decomposition of `DoclingDocument` into headings, paragraphs, tables, figures, formulas, and page objects. It is best understood as a **Docling-enabled extraction backend feeding a hybrid SQL/vector retrieval engine**, not as a Docling-native structural index. That is still valuable: among public systems, it is the strongest proof that Docling can sit underneath a local SQL-and-semantic retrieval layer without requiring a heavyweight remote service. citeturn35view0turn35view1turn35view2turn35view3

**haiku.rag** is the best public example of a Docling-aware retrieval engine that keeps more of the structure intact. Its README says it is built on **LanceDB, Pydantic AI, and Docling**, supports **hybrid search with reciprocal rank fusion**, **multimodal and cross-modal retrieval**, **visual grounding**, and—crucially—**stores the full `DoclingDocument`** for structure-aware context expansion. It is also **local-first** and uses embedded LanceDB rather than a mandatory remote service. The ingester includes a **persistent SQLite queue** for operational durability. If you wanted a serious open retrieval system that preserves Docling structure better than most, this is one of the few documented public examples. citeturn20view0turn9search0turn9search1turn9search9

The downside of haiku.rag is that it is **already a product-shaped RAG system**. It bundles MCP, analysis skills, rerankers, multiple embedding providers, and application logic. So while it is technically strong, it is **not** the “agentic-free honest lower-layer Docling indexer” you described. It is what happens when someone solved this problem for an application rather than for a clean infrastructure package. citeturn20view0

**Docling Studio** is the strongest example of a system that explicitly acknowledges the need for separate layers. It is a browser-based analysis studio powered by Docling, backed by **SQLite** for app state, with pipeline options that map directly to **Docling’s `PdfPipelineOptions`**, including OCR, table structure, formula enrichment, picture classification, picture description, picture image extraction, and page image generation. It can optionally index chunks into **OpenSearch** for **vector and full-text search**, and it can mirror the **full DoclingDocument tree into Neo4j**, creating first-class graph nodes for sections, paragraphs, tables, figures, pages, and chunks. That is precisely the kind of split architecture your question points toward: raw structured parse, search index, and queryable relational/graph metadata side by side. citeturn23view0

Docling Studio again is not a tiny reusable library, but it is important because it demonstrates that a **flat chunk store is not enough**. The project explicitly says the Neo4j mirror enables queries that are impossible with a flat chunk index, such as navigating the outline, finding all tables under a section, or tracing a chunk back to its source elements. That is one of the clearest public confirmations that this problem is real, not hypothetical. citeturn23view0

### Framework integrations that are composable but stop short of a canonical index

The official **LangChain**, **Haystack**, and **LlamaIndex** Docling integrations are useful, but they do not solve the storage design problem for you. LangChain’s `DoclingLoader` supports either **`DOC_CHUNKS`** or **`MARKDOWN`** export modes. Haystack’s `DoclingConverter` supports **chunked documents**, **Markdown**, or **JSON** export. LlamaIndex has a **`DoclingReader`** that exports as Markdown or JSON and a **`DoclingNodeParser`** that splits JSON into nodes corresponding to paragraphs, headings, tables, and so on. These are genuinely composable, and they are not total black boxes, but each one pushes you toward its own retrieval abstraction rather than defining a shared Docling-native persistence model. citeturn30view0turn30view1turn31search1turn31search2

The official Docling examples page unintentionally reinforces the same point. In its documented RAG examples and integrations, Docling prominently points users to **Milvus, Weaviate, Qdrant, OpenSearch, MongoDB + VoyageAI, Azure AI Search**, plus framework integrations like **LangChain, LlamaIndex, Haystack, and txtai**. That is a healthy ecosystem, but it also shows that the center of gravity is still **“Docling as parser feeding an existing retrieval backend”**, not **“Docling plus a canonical open local indexer.”** citeturn25view0turn6search8

### Adjacent systems that matter but are not really FTS-first

**Semantica** is a native Docling integration oriented toward semantic layers and knowledge graphs rather than document search in the narrow sense. Its Docling integration says the `DoclingParser` uses Docling’s `DocumentConverter` to extract high-fidelity Markdown and structured tables, and then Semantica builds entities and relations into a property graph such as **Neo4j** or **FalkorDB**, or into RDF triplets. This is highly relevant if your long-term aim is GraphRAG or semantic querying over extracted structure, but it is not a Docling-native FTS/semantic document index. citeturn32view0

**docling-graph** is another adjacent project worth watching. It turns documents into validated pydantic objects and then into **NetworkX** graphs with stable IDs and edge metadata, with exports to **CSV** and **Cypher** and future graph-database integration on the roadmap. Again, it confirms strong demand for “structured Docling output into queryable storage,” but it is graph-centered rather than full-text/hybrid-search centered. citeturn33view0

The official **docling-mcp** project is also revealing, because it is explicitly “making Docling agentic.” It exposes Docling conversion through MCP tools, supports remote Docling Serve or local conversion, caches locally, and mentions **Milvus upload and retrieval** for RAG applications. It is useful if you want Docling directly accessible inside client tools, but it is almost the opposite of the lower-layer, agent-agnostic index service you asked for. citeturn34view0

### App-centric stacks that prove demand but are not clean infrastructure answers

There is now a wide band of Docling-based Python applications that wrap retrieval backends on top of Docling, but most are **application stacks**, not reusable storage designs. **NexusRAG** uses Docling or Marker, **ChromaDB**, LightRAG, reranking, and page-aware image/table captioning; it appends image and table summaries into chunk text and keeps page/heading metadata, which is useful, but again it is a retrieval application rather than a neutral storage layer. citeturn21view0turn22view0

The same pattern appears in **OpenRAG** and **docling-factory**, both of which are built around **OpenSearch**; in **local-rag** and **ClawRag**, both of which are built around **ChromaDB**; and in various Milvus-based examples. These projects are valuable because they show a real and growing demand for Docling-plus-indexing, but they mostly choose an existing vector/search engine and then solve application concerns above it. They do not converge on a shared, Docling-native persistence schema. citeturn24view2turn24view3turn24view1turn24view0turn18search20turn18search3

One especially relevant signal comes from the **OpenClaw** proposal for native Docling-based document processing. That proposal explicitly argues for reusing **existing embedding pipelines** and **memory storage such as SQLite-vec or LanceDB**, instead of adding a whole separate system. In other words, your exact design instinct—Docling as parser, honest local indexing layer, separate agent layer on top—is already showing up in real project discussions. citeturn19search0turn15search8

## Storage backends that pair well with Docling

If you want **SQL-native document introspection**, SQLite is still the most attractive substrate. SQLite gives you **FTS5** for full-text search and **JSON functions/operators** for querying JSON content inside the same embedded database. The modern SQLite docs also describe **JSONB** as a binary encoding for JSON. For vectors, the current open options are external extensions such as **sqlite-vec**, which explicitly describes itself as the successor to sqlite-vss, and **sqlite-vss**, which is based on Faiss. This makes SQLite very appealing for a Docling indexer that stores raw Docling JSON plus a normalized block table and keeps both keyword and semantic retrieval local. citeturn11search0turn11search1turn11search4turn39search0turn39search1

The catch is that **SQLite is a substrate, not a finished Docling retriever**. You still need to decide the schema, indexing granularity, embedding storage representation, update strategy, and hybrid-ranking logic. That is exactly why there is so much reinvention. SQLite makes the system elegant, but it does not tell you what the “right” relational image of a `DoclingDocument` should be. The public projects I found do not yet converge on one. The best signal of demand is the OpenClaw proposal’s explicit mention of **SQLite-vec or LanceDB** as the desired reusable storage layer. citeturn19search0turn15search8

If you want **analytical SQL, Parquet, and lakehouse-style metadata management**, DuckDB is an unusually good match. DuckDB has an official **FTS extension**, an **experimental VSS extension**, efficient **Parquet read/write support**, and an official **Iceberg extension** for reading and working with Iceberg tables. That makes DuckDB a strong candidate for the **document metadata and analytics layer** in a Docling indexer, especially if you want to preserve raw or normalized block data in **Parquet** and keep SQL introspection first-class. citeturn10search0turn10search4turn10search1turn10search3turn13search0

What DuckDB does **not** currently give you is an already-popular, public **Docling+DuckDB retrieval package** comparable to txtai or haiku.rag. Based on the public projects and official examples surfaced in this survey, DuckDB looks more like the **best build target** than the **current ecosystem default**. That is a gap, not a weakness of DuckDB itself. The primitives are there. citeturn10search0turn10search4turn13search0

If you prioritize **embedded hybrid retrieval and multimodal search**, LanceDB is currently the strongest substrate. The official docs say LanceDB supports **full-text search**, **vector search**, **hybrid search**, and **SQL filtering** in one table, and the underlying Lance format is positioned as an open hybrid-search and analytics format with support for multimodal data and integration with **DuckDB**. This is why projects like haiku.rag land there: LanceDB is very strong for the actual search path. The tradeoff is that it is not a simple relational database in the SQLite sense, so if rich SQL document introspection is a primary requirement, many teams will still want a sidecar relational layer. citeturn9search0turn9search1turn9search9turn9search6turn39search10

If you specifically like **Tantivy**, the Python bindings exist and are mature enough to use as a real FTS component. But Tantivy is only the **full-text** half of the problem. The official Python bindings position it as Python bindings to the Rust full-text search engine; they do not solve metadata storage, semantic search, or Docling mapping for you. In practice, a Docling+Tantivy design still needs a separate relational store and a separate vector strategy. That makes it a good low-level choice for people who want control, but not a complete answer by itself. citeturn39search2turn39search9

## Why this gap keeps getting reinvented

The short answer is that the problem is **conceptually simple but schema-wise annoying**. It is easy to say “parse with Docling, then do FTS and embeddings.” It is much harder to decide what the stable searchable unit should be: page, heading section, paragraph, table, figure, caption, formula block, or some synthetic chunk composed from several of those. The public integrations prove this fragmentation. LangChain exposes **chunks or Markdown**; Haystack exposes **chunks, Markdown, or JSON**; LlamaIndex exports JSON and then splits it into nodes like paragraphs, headings, and tables. Each project picks its own flattening boundary because Docling is richer than a plain text splitter. citeturn30view0turn30view1turn31search1turn31search2

A second reason is that **flat chunk stores are operationally convenient but structurally lossy**. haiku.rag had to explicitly add storage of the full `DoclingDocument` to enable structure-aware context expansion. Docling Studio had to explicitly mirror the document tree into Neo4j because a flat chunk store cannot answer structural questions such as “all tables under this section” or “which source elements produced this chunk.” That is strong public evidence that ordinary chunk-vector pipelines are not enough once you care about tables, figures, provenance, and navigable structure. citeturn20view0turn23view0

A third reason is that **the storage backends each want a different shape**. SQLite wants tables and maybe JSON columns; DuckDB wants columnar analytics and can happily read/write Parquet or Iceberg; LanceDB wants one or more search tables with vectors, text, and filterable fields; Tantivy wants explicit FTS field mappings; service backends like OpenSearch want index mappings and often encourage app-centric ingestion. So even when the parser is shared, the target schema is not. That multiplies reinvention. citeturn11search0turn11search1turn10search0turn10search4turn13search0turn9search0turn39search2

My own read, based on this survey, is that the hard part is **not building a usable v1**. A solid v1 is honestly moderate in difficulty if you avoid a full one-to-one SQL mapping of the entire Docling JSON. The hard part is building the version that everyone would actually agree to depend on: schema evolution, incremental reindexing, robust multimodal provenance, hybrid ranking, Office/Markdown/PDF differences, and enough SQL ergonomics that users do not immediately fork it for their own domain. The public diversity of Docling-based retrievers strongly suggests that this “last 20%” is where most of the reinvention happens. citeturn14search9turn29search5turn20view0turn23view0turn30view0turn30view1turn31search2

## A practical design for the honest Docling indexer you want

The most credible design, in light of the ecosystem above, is **not** “map every Docling JSON node to a SQL table.” It is:

Store the **raw `DoclingDocument` JSON** intact, so nothing is lost. Then normalize only a **logical-block layer** that is stable enough for retrieval: heading, paragraph, table, picture, code block, formula, list block, and optionally page. That matches both Docling’s own document model and what the LlamaIndex Docling node parser already treats as meaningful document elements. citeturn14search9turn31search2

For each logical block, keep a small, durable schema: `block_id`, `doc_id`, `block_type`, `page_numbers`, `heading_path`, `parent_block_id`, `source_element_refs`, `bbox_json`, `text`, `search_text`, and `attrs_json`. Then keep side tables for `table_metadata` and `picture_metadata`, where table summaries, row/column dims, picture class labels, picture captions, and image asset references live. That lets you index **logical block granularity** while still preserving enough structure to do provenance, UI jumps, page citations, and multimodal retrieval.

For Markdown, DOCX, PPTX, XLSX, and HTML, do **parser-native structural indexing** whenever possible instead of forcing everything through a Markdown round-trip. The Docling paper is explicit that markup-based formats preserve semantics and pass through direct parser backends. That means your indexing policy should distinguish markup-origin blocks from OCR-derived blocks. A Docling-native indexer should know whether a table came from semantic markup or from recovered PDF structure, because confidence, cleanup rules, and chunking policy will differ. citeturn29search5turn14search6

For the actual storage layer, the cleanest options are these:

A **SQLite-first stack** is the best fit if you want one local file and maximum introspection. Use SQLite tables for documents and blocks, **FTS5** for lexical search, **JSON1/JSONB** for raw structure and block attributes, and **sqlite-vec** if you want everything embedded. This is the most “honest indexer” path. It is simple to operate and excellent for MCP exposure later because every piece is queryable by normal SQL. citeturn11search0turn11search1turn11search4turn39search0

A **DuckDB-first stack** is the best fit if you want SQL analytics over block metadata plus Parquet/Iceberg interoperability. Use DuckDB tables for documents and blocks, the **FTS** extension for lexical retrieval, the **VSS** extension where acceptable, and periodically materialize normalized block tables to **Parquet**. This is especially attractive if document stores are large, you want ad hoc analytics, or you want to join retrieval metadata with structured warehouse data. citeturn10search0turn10search4turn10search1turn10search3turn13search0

A **LanceDB-plus-SQL-sidecar** stack is the best fit if retrieval quality and multimodality matter most. Put text, captions, and multimodal embeddings in LanceDB; keep richer metadata and raw Docling JSON in SQLite or DuckDB. This is effectively the direction haiku.rag demonstrates, even if he packages it in a more opinionated application form. citeturn20view0turn9search0turn9search1turn9search9turn9search6

If you do this, I would strongly recommend **against** exhaustive item-level SQL mapping on day one. Your own intuition is right: it is too much surface area for uncertain upside. A **block-level schema plus raw JSON sidecar** is the sweet spot. You keep all future flexibility, but you also get something simple enough that other people might actually adopt it instead of reimplementing it. The public projects that seem healthiest today all either preserve the full Docling output somewhere or keep a way back to it. citeturn20view0turn23view0turn31search1turn31search2

## Open questions and limits

This survey is strong on **publicly documented Python projects and official docs**, but it is not a census of every private repo or unpublished internal tool using Docling. The largest uncertainty is not around Docling itself, but around lightly documented community projects whose READMEs describe capabilities without exposing schema internals. citeturn25view0turn23view0turn20view0

I found **clear evidence** for Docling paired with **txtai, LanceDB, OpenSearch, ChromaDB, Milvus, LightRAG, Neo4j, and NetworkX**. I found **much weaker public evidence** for mature Docling stacks centered on **SQLite-vec**, **DuckDB VSS**, or **Tantivy** as the primary downstream index, even though all of those building blocks are technically viable and, in my judgment, promising. So the gap you are describing is real: the substrate exists, but the clean open “Docling-native honest indexer” still looks underbuilt. citeturn35view0turn20view0turn23view0turn21view0turn24view2turn24view3turn24view1turn34view0turn39search0turn10search4turn39search2

The practical takeaway is simple: **this is not too hard to build**, but it is still hard to standardize. If you want the shortest path to something usable today, start from **txtai** or from a **SQLite/DuckDB + Docling logical-block schema** of your own. If you want the strongest retrieval substrate today, start from **haiku.rag’s LanceDB-shaped design**. If you want the cleanest proof of a full structural mirror, study **Docling Studio’s SQLite + OpenSearch + Neo4j split**. Those three together are the best public map of the space right now. citeturn35view0turn20view0turn23view0
